二、产品目标
Caelis 将构建拥有身份、偏好和持续对话的个人助手 Bot。用户不需要管理 workspace 或工作 Session；Bot 内部可以委托 Agent 执行工作，并在后续对话中使用长期信息。
Memory v0.6.0 要支撑的核心体验是：
用户明确表达的事实能够跨对话保存、正确采用、随时间更新、解释来源，并在被纠正、否认或遗忘后停止被错误使用。

典型场景：
1. “我平时喝咖啡。”跨新对话和重启后仍可使用。
2. “这周先不喝咖啡。”形成临时例外，下周恢复长期习惯。
3. “以后改喝茶。”更新当前偏好，同时能解释过去的变化。
4. “我从没说过喜欢咖啡，是你理解错了。”纠正错误，不描述成用户后来改变习惯。
5. “帮朋友选素食餐厅。”不能被记成用户是素食者。
6. 用户遗忘一项事实后，整理任务、历史派生和索引重建不能将其重新带回。
7. 用户换一种说法询问，能够找到经过验证的相关事实。
8. 没有证据时返回不足或未知，不用常识补出用户事实。
首版只保证明确摄入的证据和受支持场景。不要承诺能够回忆从未提交给 Memory 的全部聊天历史。
三、范围与约束
必须保持
- Memory 独立版本演进，不依赖 Caelis 的 Bot、Session、workspace 等产品类型。
- SQLite 与现有嵌入式运行形态。
- 不增加向量数据库、图数据库或其他外部中间件。
- 不要求用户部署新服务、下载 embedding 模型或安装本地推理运行时。
- Caelis 将 Memory 编入自己的二进制，不引入 Memory sidecar。
- Memory 拥有记忆领域的协议、整理政策、提案验证、持久化和授权。
- 宿主拥有模型选择、凭据、调用预算、生产者适配和上下文装配。
- 模型输出是提案，不能成为持久化、删除或权限升级的直接授权。
本里程碑不实现
- 完整 Corpus、Leaf 协议和全量 Session 导入；
- 层级摘要树、实体图和复杂投影平台；
- 默认 embedding、常驻模型重排服务；
- 自动学习宿主系统指令；
- Bot、定时任务、通知或桌面界面；
- 跨机器复制及新的独立服务发行形态。
可以复用现有机制，也可以调整以下设计建议。接口名和字段名不是硬性要求，但用户可观察语义及验收目标必须落实。
四、开工方式
先完成一次短的代码核对和设计收敛，然后直接实施，无需再次开展大型外部调研。
重点核实以下评审发现：
- 当前 Recall 是否会把被替代 Record 对应的原始 Receipt 继续作为独立候选返回；
- 当前删除是否仅使 active Record 失效，而未清理历史 Revision 内容；
- 公开嵌入式 Management facade 是否缺少现有内部治理能力；
- Steward 上下文是否只按更新时间选择最近 Records；
- 在途整理是否验证实际读取的全部依赖；
- 当前时间字段和采用状态能否表达临时例外及事实变化。
把确认的问题转成测试。对尚未复现的并发风险，先构造生产形状的确定性测试，不直接宣称为已证实漏洞。
按照下面 M01–M07 维护进度和证据。每个任务由同一负责人完成实现、测试和必要文档，避免按文件类型拆成零散流水线。
五、实现任务
M01：当前事实协议、数据模型与迁移
目标：区分原始证据和当前可采用事实，建立后续功能共同契约。
建议入口：
- api/memory/*
- internal/appliance/semantic_schema.go
- internal/appliance/schema_baseline.go
- appliance/runtime.go
实现要求：
1. 保留旧 Remember/Recall 的证据检索及 read-your-writes 语义。
2. 提供版本化的当前事实读取契约，不静默改变旧接口含义。
3. 在现有 Record/Revision 上扩展必要语义，不另建一套独立画像真相库。
4. 支持主体、事实类型或键、来源依据、采用状态、有效区间、适用条件及证据/替代关联。
5. 事件可以仍以文本表达，不强制所有记忆变成键值对。
6. 明确长期变化、临时例外、纠错、否认和遗忘的区别。
7. 条件保持有限、可测试；无法解释的自由文本条件不能自动当作确定匹配。
8. 实现显式存储迁移与兼容策略。
迁移要求：
- 旧数据不自动升级为“用户确认”。
- updated_at 不自动变成事实生效时间。
- 未知信息保持未知。
- 迁移中断后可恢复。
- 明确旧二进制遇到新 schema 的行为，不假设降级可安全写入。
验收：
- 固定 v0.5.2 夹具升级后，Receipt、幂等、来源关联、隔离和旧 Recall 行为保持兼容。
- 新公开 API 可由独立外部 Go module 使用。
- 状态转换、错误语义和迁移边界有 owning tests。
M02：公开治理与遗忘屏障
目标：通过正式公开接口完成查看、解释、纠正、否认和遗忘。
建议入口：
- appliance/runtime.go
- internal/appliance/governance.go
- inspect.go
- steward.go
- steward_jobs.go
- restore.go
- api/memory/management
- conformance
实现要求：
1. 为嵌入式宿主暴露完整治理能力，不依赖内部包或临时类型断言。
2. 区分纠正错误、修改当前事实、拒绝推断和遗忘。
3. 建立逻辑失效屏障：先停止新读取和派生发布，再执行受管清理。
4. 清理覆盖相关历史 Revision、索引、待处理派生结果。
5. 提供变更/失效版本或游标，以及清理状态。
6. 整理提交检查实际读取的依赖集，不能只相信模型填写的 evidence refs。
7. 重启后继续未完成清理。
8. 明确备份恢复与外部副本边界。
验收：
- 外部 module 只用公开 Runtime 即可完成治理。
- 在整理读取后、提交前精确暂停，执行遗忘再放行，派生不能复活。
- 清理中退出并重开后行为正确。
- 历史派生和索引不能继续暴露已遗忘内容。
- 不把“当前检索无命中”当作完整清理证明。
保证范围是受管数据和受支持重建路径的逻辑遗忘，不是外部供应商、用户导出文件和所有磁盘介质的取证级擦除。
M03：可信证据、来源身份与摄入策略
目标：让记忆具有可核对的来源，并阻止错误归因和重复摄入。
实现要求：
1. 增加可信宿主的证据提交入口，表达 producer、source event/revision、片段定位、主体和来源角色。
2. 来源可信属性由宿主传入，模型不能通过正文自报“用户确认”。
3. 区分用户原话、结构化确认、可核验观察和模型推断。
4. 增加来源去重与遗忘抑制；换调用幂等键不能绕过同一来源的抑制。
5. 提供未来摄入策略及可解释拒绝原因。
6. 结构化用户编辑不依赖文本模型在线。
验收：
- 同来源不同内容冲突。
- 同来源换幂等键不复活。
- 被禁止的摄入不产生新的 Receipt 或整理任务。
- 相似文本不能跨主体或分区串写。
- “替朋友选素食”不被自动提升为用户饮食事实。
不要宣称能够确定识别任意改写后的同义内容；来源抑制必须有清楚边界。
M04：相关事实整理与事实演变
目标：长期积累后仍能找到需要更新的旧事实，并正确处理变化。
实现要求：
1. 复用 Steward，使用同主体/事实键、FTS 相关候选和少量最近记录选择上下文。
2. 不仅扩大最近 Records 数量。
3. 支持有界多事实提案，以及原子验证和应用。
4. Memory 继续拥有 prompt、parser 和政策。
5. 并发更新验证读取版本；冲突后重新整理，不能盲目覆盖。
6. 区分证据接受、待整理、事实生效和拒绝。
7. 推断默认待确认，不因模型给出高 confidence 就成为用户事实。
验收：
- 很久以前的偏好被大量无关内容挤出最近窗口后，仍可正确更新。
- 临时例外不永久覆盖长期习惯。
- 永久变化保留历史查询能力。
- 纠错不会被解释为事实随时间变化。
- 多操作提案存在越权或 stale 目标时不会部分提交。
- Steward 禁用时保持零模型基线，并返回真实的整理状态。
M05：当前事实、历史查询与有限背景
目标：先保证取到的是正确事实，再改善自然改述召回。
实现要求：
1. 区分当前个性化、历史回忆和原始证据查询用途。
2. 当前事实路径不无差别混入旧 Receipt。
3. 在授权范围内检查主体、采用状态、有效期和适用条件。
4. 有限背景从当前事实确定性选择和格式化，不生成另一份独立可编辑画像。
5. 返回事实版本、证据、失效依赖和预算裁剪信息。
6. 当前事实变化后，背景可被宿主及时刷新。
7. 先实现事实键、受控别名和词法组合。
8. 查询改写仅在对照实验有收益时引入，保留原查询候选，并有明确调用预算和退化行为。
验收：
- 当前查询采用新偏好，历史查询能解释旧偏好。
- 遗忘和否认内容不进入背景。
- 相同版本、请求和预算下背景尽量稳定。
- 不扩大 Space/LabelSet 权限。
- 不将不同分区 BM25 分数当作统一概率。
- 无模型模式下，结构化读取与词法路径继续工作。
M06：纵向质量与可靠性评测
目标：用真实长期轨迹验证改动，不以关键词命中替代长期记忆质量。
先建立小型关键行为阻断集，再扩展到至少 200 条经过人工审阅的纵向轨迹。可以生成候选夹具，但未经人工审阅的材料不能标记为人工金标准；如缺少审阅条件，明确保留该发行门槛，不伪造完成。
轨迹至少覆盖：
- 多次对话、干扰记录和重启后的偏好使用；
- 临时例外、永久变化、过去与现在；
- 错误主体和用户否认；
- 同义、间接及中英混合表达；
- 删除期间的在途整理、重建和重放；
- 不存在的事实与正确拒答；
- 多主体、多分区隔离。
对照组：
- B0：v0.5.2，无 Steward；
- B1：现有 Steward；
- C1：新事实生命周期；
- C2：相关事实整理；
- C3：别名或有预算改写。
固定数据、模型、profile 和输出预算。分别测量抽取、检索、背景和消费端回答；模型自评不能作为唯一正确性依据。
验收目标：
- 关键确定性行为全部通过。
- 测试覆盖的越权、受管删除复活为零，来源引用有效。
- 明确偏好采用正确率目标 ≥95%。
- 自然改述 Recall@8 目标 ≥90%。
- 同时报告错误记忆、陈旧采用、遗漏和拒答，不能只优化召回。
- 阈值和验收集在调参前冻结，不因结果不达标而静默修改。
性能覆盖单热点分区 1k、10k、100k 证据，记录：
- 冷热查询及写入竞争；
- 整理积压、清理和重建；
- p50/p95/p99、RSS、数据库与索引大小；
- 模型调用量、token 和无效整理比例。
性能门槛在基线实验后、优化前固定，绑定硬件和数据规模。不把未测数据写成成绩。
M07：消费验证与 v0.6.0 发行准备
目标：形成可发行的独立 Memory 版本，并证明公开能力可被 Caelis 正确消费。
顺序：
1. 固定精确候选 SHA 或明确的待提交工作树快照。
2. 完成 Memory gates 和新纵向评测。
3. 使用候选公开 API 完成消费测试。
4. 准备版本、schema floor、迁移与兼容说明。
5. 准备 release notes 和发行清单。
6. 在实际发布前等待单独授权。
不得让消费验证变成循环依赖：Caelis 可以先验证 Memory 候选，Memory 正式发行后再升级 Caelis 正式依赖。
本任务可以只读检查 Caelis。需要验证宿主接入时，可在临时目录或独立测试副本中编写消费 harness，不修改共享 Caelis 工作树，不提前实施 Bot。临时 replace/go.work 不能进入发行交付物。
如果 Memory facade 与消费契约必须调整，应在本里程碑内完成；如果发现 Caelis 自身需要改动，则交付具体接入任务、代码位置及测试要求，不以临时绕过宣称端到端完成。
六、与 Caelis 的接口交付要求
本里程碑至少要交付足够支撑以下消费方式的公开契约和测试：
- Host 选择稳定主体及记忆范围。
- Bot 私有与项目记忆分别授权、读取和组合。
- 只读工作不获得 Remember 或治理权限。
- Host 提交选定来源证据。
- Host 获取有限背景及依赖标识。
- 用户通过授权管理入口纠正、否认和遗忘。
- Host 观察变更，使缓存和后续模型上下文失效。
Memory 不负责直接修改 Caelis Session JSONL，也不把 Caelis 的历史存储格式写入协议。需要明确通知消费端：
- 哪些版本或来源已失效；
- 什么时刻开始禁止采用；
- 如何检测漏掉变更；
- 清理完成意味着什么；
- 已经发给模型的上下文无法撤回。
Memory 内部遗忘通过，不等于 Caelis 的历史回放和上下文副本已经完成清理。 两类验收分开报告。
七、验证与发布规则
遵循仓库当前发布流程。预计至少包括：
make check
make race
make durable
make corpus-gate
make ga-soak
- GA soak 在最终候选阶段执行。
- 新增长期事实 gate，不能假定旧 corpus-gate 已覆盖新语义。
- 原生 Windows embedded Open 证据不能用交叉编译替代。
- 保持发布所需 CGO_ENABLED=0 路径有效。
- 跨仓库独立解析使用 GOWORK=off。
- 并发测试使用明确屏障或可控时钟，不依赖随机 sleep。
- 迁移、持久化和故障恢复使用生产形状测试。
- 只在新增修改或失败需要时重复昂贵验证。
当前目标版本为 v0.6.0。如果该版本已发行，核实发行线并说明调整，不能覆盖 tag。
